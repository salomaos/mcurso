# mcurso

App pessoal (single user) para criar e gerenciar apostilas de aula. UI, código e commits em pt-BR. **`main` é produção, `dev` é onde se trabalha** (ver "Git"), commits com Conventional Commits.

## Git

### O commit é do usuário, nunca do agente

**Nunca rode `git commit` nem `git push` por conta própria.** O agente implementa, roda `npm run check`/`npm run test`/E2E, e **para**: mostra o que mudou (arquivos e pontos de decisão) e espera o usuário revisar e pedir o commit ("pode commitar"). Só então commita — e o push, se pedido junto ou depois. Vale mesmo com os testes verdes e a mudança "obviamente" pronta: a revisão do diff pelo usuário é parte do fluxo, não uma etapa opcional. Vale também para mudança pequena, documentação, correção de typo e commit de teste — nada de "já que estava ali".

### `main` é produção, `dev` é onde se trabalha

- **`main` é a branch publicada** e é a **branch conectada no deploy da Hostinger**: o auto-deploy dispara no *push* para a branch conectada (hPanel → Deploy → Deployment settings → Branch), então push na `main` = subir para o ar.
- **`dev` é o trabalho do dia a dia** (`feature/*` quando a mudança for grande). Nada entra na `main` por push direto: entra por **pull request**.
- Quem exige o PR é a **ruleset do GitHub** (Settings → Rules → Rulesets, alvo `main`): *Require a pull request before merging* (**0 aprovações** — quem abre o PR mergeia o próprio), *Block force pushes* e *Restrict deletions*, **sem bypass**. Ela vale de graça porque **o repo é público** (ruleset em repo privado exigiria GitHub Pro) e é do lado do servidor: pega o terminal e o agente, sem depender de disciplina.
- **Fluxo**: commit na `dev` → push da `dev` → PR `dev` → `main` → merge → **o merge dispara o deploy**. Commitar e pushar na `dev` não sobe nada. Se a ruleset cair por algum motivo (plano, repo virar privado), o mínimo continua sendo **nunca push direto na `main`**.

## Stack (decisões acordadas)

- **SvelteKit 2 / Svelte 5** + **adapter-node** (SSR/Node). O `vite.config.ts` força **runes mode** em todo o app (`runes: true` para tudo fora de `node_modules`): componente novo já nasce com `$state`/`$derived`/`$props`/`$effect`, sem `export let`/`$:` legado. Scaffold: `npm create sv@latest`
- Node 24, **npm** (migrou de pnpm em 29/10/2026: `pnpm-lock.yaml` e `pnpm-workspace.yaml` foram removidos — não reintroduzir nem documentar comandos pnpm)
- **Drizzle ORM** com **SQLite** (dev) ou **MySQL/MariaDB** (hospedagem), **escolhido por deploy** com `DB_DIALECT=sqlite|mysql` — não é escolha de runtime, é de ambiente. No SQLite o driver é o `node:sqlite` do Node ≥ 22.13 (**sem binário nativo** — ver quirks); no MySQL o driver é o `mysql2` (JS puro). Migrations geradas com `drizzle-kit` e **aplicadas no boot do app** (`db/migrar.ts`), não por passo separado de deploy — `drizzle/` no SQLite, `drizzle-mysql/` no MySQL. Os dois schemas vivem lado a lado (`schema.ts`/`schema.mysql.ts` e os dois auth-schemas), com o `schema-paridade.test.ts` guardando o contrato. PostgreSQL está descartado.
- **Better Auth** com adapter Drizzle; login por **senha mestra** — usuário único professor, sem registro/2FA
- CSS: **`@ahmartecnologias/ahmardesign`** (Vanilla CSS). Tema padrão `brutalist` + seletor de tema
- Diagramas: **Mermaid**. Código: **highlight.js**. Fórmulas: **KaTeX**
- Testes: **Vitest** (unit/integration) + **Playwright** (E2E)

Gêmeos para o MySQL: `npm run db:generate:mysql` e `npm run db:migrate:mysql` (o `drizzle.mysql.config.ts` usa `DB_URL`). O `drizzle.config.ts` carrega `dotenv/config` e usa `DB_PATH` — com o `node:sqlite` (ver quirks) o `db:migrate` manual pode falhar por falta do pacote real do better-sqlite3; não é problema, o app migra no boot
- **Banco local em MySQL/MariaDB** (mesma versão da hospedagem): `docker compose up -d` — MariaDB **11.8.9**, porta **3307** no host (aceita `PORTA_BANCO`), root `mcurso`, usuário do app `mcurso`/`mcurso` (ALL só no banco `mcurso`), banco `mcurso` criado vazio, `utf8mb4`/`utf8mb4_unicode_ci`, volume `dados`. Para rodar o app contra ele (PowerShell): `$env:DB_DIALECT='mysql'; $env:DB_URL='mysql://mcurso:mcurso@127.0.0.1:3307/mcurso'; npm run dev` (o `.env` de SQLite fica intacto: o `dotenv` não sobrescreve o que já está no ambiente)
- **E2E**: `npx playwright test` roda a suíte inteira — sem argumento e sem `testIgnore` especial (os arquivos de repro que quebravam a coleta foram removidos em 16/10/2026). Para um subconjunto, passe as specs: `npx playwright test e2e/fluxo.spec.ts e2e/quiz.spec.ts`
  - Suíte (17 specs): `apresentacao`, `arrastar`, `busca`, `fluxo`, `tema`, `anexos`, `exercicios`, `inserir-bloco`, `link`, `markdown`, `rodape`, `simulacao`, `visao`, `quiz`, `importacao`, `html` e `uploads`
  - **A mesma suíte roda no MySQL/MariaDB**: com o banco local de pé, basta `E2E_DIALECT=mysql` — o `E2E_DB_URL` default (`e2e/ambiente.ts`) já aponta para `mysql://root:mcurso@127.0.0.1:3307/mcurso_e2e`. Para outro servidor, `E2E_DB_URL=mysql://root:senha@host:3306/mcurso_e2e` (o banco precisa terminar em `_e2e` — é a trava do reset contra apagar um banco de verdade — e o usuário precisa poder criar/apagar bancos: o reset faz `drop`/`create`). É essa execução que prova o dialeto de ponta a ponta. Env var de shell **não** sobrevive entre comandos: passe as duas no mesmo comando
  - **E2E nunca toca no banco dev**: o `webServer` roda `node scripts/e2e-reset.mjs && npm run build && node build` (**reset antes do build**, porque o build fala com o banco — ver quirks), recriando o banco de E2E a cada execução — `data/e2e.db` e `data/e2e-uploads` no SQLite, `drop`/`create database` no MySQL (porta 5179, `workers: 1`, `fullyParallel: false`, `retries: 0`). Sem `drizzle-kit migrate`: o app migra sozinho no boot, então o E2E exercita o mesmo caminho do deploy. As variáveis vivem em `e2e/ambiente.ts` e o `env` do `webServer` sobrescreve o `.env` de propósito (`dotenv` não sobrescreve, então nunca usar `process.env.X ?? ...` para isolar)
  - Para iterar rápido, sobe o servidor à mão contra o banco descartável e deixa o Playwright **reaproveitar** (`reuseExistingServer` já é ligado fora de CI): buildar uma vez, `node scripts/e2e-reset.mjs` com o `DB_DIALECT` do alvo, subir `node build` com o mesmo `env` do `webServer` (porta 5179) e rodar as specs — cada rodada custa segundos em vez do build de cada vez
- Unit (`vitest.config.ts`) só coleta `src/**/*.{test,spec}.{js,ts}` e exclui `e2e/**`, com `environment: 'node'`

## Modelo de dados

### Geral

- **O banco é escolha de deploy (`DB_DIALECT=sqlite|mysql`)** e o código **não ramifica por dialeto** em lugar nenhum, exceto em dois módulos de `src/lib/server/db/`: **`tabelas.ts`** (os objetos de tabela do dialeto em uso — *quem consulta importa daqui*, nunca de `schema.ts`/`schema.mysql.ts`) e **`inserir.ts`** (`inserirId`, o insert que devolve o id gerado). Os dois existem porque o **objeto da tabela carrega o mapa de valores da coluna**: o `mode: 'timestamp'` do SQLite grava segundos e mandava `1792241512` para a coluna `datetime` do MySQL (`Incorrect datetime value`), então usar a tabela do SQLite no driver do MySQL não funciona; e o MySQL **não tem `.returning()`** no builder do insert (o drizzle só oferece `$returningId()`, que devolve a PK pelo `insertId` do driver). O tipo continua sendo o do SQLite (`db` é o drizzle do SQLite; o MySQL entra por cast) — o que muda em runtime é o objeto da tabela, e a garantia real vem de rodar a mesma suíte E2E nos dois dialetos
- Apostilas **soltas** (sem hierarquia de curso) organizadas por **aulas/encontros**
- Sessão em `event.locals` via `src/hooks.server.ts` (Better Auth); escrita protegida por `requerSessao()` (`$lib/server/guard.ts`) chamada no load/action — não proteger só o markup
- O usuário professor é criado no primeiro login a partir de `APP_MASTER_EMAIL`/`APP_MASTER_PASSWORD`. Trocar a senha mestra depois **não** remixa o hash guardado: o usuário precisa ser resetado
- **Anexos são soltos**: tabela `anexos` independente, **sem** vínculo de posse com apostila ou aula. O aluno chega neles por link dentro de uma aula; eles não aparecem em listagem de aulas, painel da apostila nem no índice. Referência não é posse: `/anexos` lista em quais aulas o anexo é usado (único por aula) e a action devolve **409** ao excluir anexo em uso, pedindo para remover os links
- Conteúdos (aula/anexo/atividade) compartilham blocos, editor e leitura: usar `src/lib/components/{Editor,Visualizar}Conteudo.svelte` + `src/lib/server/conteudo.ts` (parsing/validação) em vez de duplicar rota/componente. `TipoConteudo` é só conceito de UI
- Rotas de anexo na raiz: `/anexos/[anexoId]` (+ `editar`, `imprimir`, `apresentar`); leitura/impressão/apresentação são públicas, edição e `/anexos` exigem sessão. `caminhoAula()`/`caminhoAnexo()` em `src/lib/conteudo.ts` montam as URLs
- Link interno é genérico: `BlocoLink.alvoId` (+ `tipoLink`, sem `alvoApostilaId`). Link de anexo aponta para `/anexos/[id]` e funciona em qualquer apostila; link de aula precisa da apostila do bloco e o `EditorConteudo` passa o `contexto` ao editor. Picker: `alvosParaLinks()` na aula (aulas da apostila + anexos + atividades) e `alvosAnexos()` no anexo (só anexos). Arquivo externo é `tipoLink: 'externo'`
- **Seções** são catálogo normalizado: tabela `secoes` (`id`, `apostilaId`, `nome`, `ordem`) e `aulas.secaoId` nullable; CRUD no painel da apostila, select no editor, agrupamento na listagem. Nome único por apostila (comparação sem acento/caixa, máx. 120 = `LIMITE_NOME_SECAO`, com `maxlength` nos três inputs de seção) e ordenado por `ordem`, com grupo "sem seção" no fim. O SQL do painel (carregar aulas/seções, CRUD de seção, reordenação e exclusão — as 4 transações da rota) fica em `src/lib/server/apostila.ts`: a rota só lê o FormData e traduz o `FalhaPainel` (a `Falha` de `conteudo.ts` + `alvo?: 'secao'`, que a página usa para decidir onde mostrar o aviso)
- SQLite não liga `PRAGMA foreign_keys`: ações que apagam seção/apostila/nullam `aulas.secaoId` por conta própria
- **Sem draft/publicado e sem histórico**: edição direta, versão única
- **Ordenação por drag and drop**: blocos (posição no JSON), aulas (`ordem`) e seções (`ordem`). Cada soltar envia a lista inteira para uma action `?/reordenar*` (valida pertencer à apostila) e renumera em transação
- PDF: rota SSR própria com `@media print`, uma página por aula/anexo/atividade; usuário imprime com Ctrl+P (sem geração server-side)

### Atividades de exercício (`/exercicios`)

Terceiro conteúdo solto, montado com os mesmos blocos; a parte pública é diferente de aula/anexo. `TipoConteudo: 'exercicio'` com `ROTULO_TIPO` = "Atividade"; rota pública `/exercicios/[id]`

- **O gabarito não sai do servidor**: `buscarExercicioPublico()` monta as questões com `questoesPublicas()` (`$lib/corrigir.ts`, que só produz `{id, pergunta, alternativas, selecao}` — sem `correta`/`explicacao`) e a action `?/responder` corrige no POST via `corrigirExercicio()`. Nunca passar o bloco inteiro ao componente `Questao.svelte`
- **Duas modalidades de escolha**: `BlocoExercicio.selecao` = `radio` (uma correta) ou `checkbox` (várias). `correta` é número no rádio e lista no checkbox; bloco antigo (sem o campo) é rádio. `corretasDoExercicio()` normaliza os dois formatos em lista ordenada (descarta índice fora da faixa, usada por editor, correção e hash) e o `normalizarCamposBloco` grava sempre no formato da modalidade
- Múltipla escolha exige **conjunto exato**: marcar a certa e mais uma já é errado. No checkbox a resposta chega em `q_<id>` repetido (`form.getAll`), no rádio em um valor só
- **Dissertativa** é o bloco `dissertativa` (`pergunta` + `orientacao`): resposta aberta, **fora da nota automática** (não conta em `acertos`/`total`). No POST vem em `d_<id>` (limite `LIMITE_DISSERTATIVA`); fora da atividade é só rascunho efêmero. A resposta volta no resultado em `textarea` somente leitura (assim imprime)
- **Fórmula em alternativa**: o conteúdo entre `$` e `$` (`$lib/matematica.ts` → `TextoMatematico.svelte`) sai com KaTeX, mantendo a alternativa como string só no banco. No PNG do resultado aparece o LaTeX cru (canvas não desenha KaTeX)
- **Nome do aluno em `sessionStorage`** (`$lib/nome-aluno.ts`, nunca servidor): sobrevive a recarregar e some ao fechar o navegador. Guardar no `oninput`, ler no `onMount` (não existe no SSR)
- Resultado marca **quais alternativas foram selecionadas** (badge "selecionada" + gabarito) no HTML, no PNG (`[x]`/`[ ]` + "gabarito", para sobreviver a tons de cinza) e no papel
- Impressão do resultado: botão "Imprimir / PDF" com `window.print()` — sem dependência. `@media print` no `app.css` (`.no-print` esconde botões, `.quebra-pagina` não corta pergunta no meio); `print-color-adjust: exact` é global, então as cores do gabarito saem
- Sem persistência: o resultado volta no `form` da própria action. Resposta em branco ou índice fora da faixa é zero, não erro (`Number('')` é `0` — descartar string vazia antes)
- **Chave de integridade** (`$lib/server/chave.ts`): HMAC-SHA256 com `BETTER_AUTH_SECRET` e rótulo de domínio `mcurso:chave-resultado:v1`, formato `base64url(payload).assinatura`. Carrega nome, quando, atividade, apostila/aula, acertos, total e `hashGabarito()` (por questão, os índices corretos unidos com `+`; questões separadas por `|`, ex.: `0+2|1`, e só entra bloco de exercício). É base64, **não criptografia**; a tela de validação (futura) lê e confere a assinatura. Não cobre as respostas discursivas (a chave é da nota)
- Contexto de origem por `?aula=<id>`: o link de atividade posto dentro de uma aula gera a query (`hrefLinkInterno` com `aulaContexto`), o `BlocoRender`/`VisualizarConteudo` repassam `aulaContexto`. É isso que a chave registra. Sem `?aula=` na URL não existe apostila: a página do aluno repassa `data.contexto.aula?.apostilaId` ao `ListaBlocos` e, sem ela, `hrefLinkInterno` devolve `null` de propósito
- Resultado vira PNG no cliente com Canvas em `$lib/imagem.ts` (sem `html-to-image`, fontes só genéricas; o card é texto puro — não desenha imagem de bloco)
- Atividade em uso não pode ser excluída (409), igual ao anexo; `/exercicios` lista em quais aulas é usada. Atenção ao nome do campo na listagem: `ExercicioUi.discursivas` (sem o "t"), enquanto a correção usa `Correcao.dissertativas` — não padronizar sem mexer nos dois lados
- **Atividade sem bloco de exercício/dissertativa não salva**: a action `?/salvar` devolve `fail(400)` e não redireciona

### Quiz estilo Kahoot (`/quiz`)

Quarto conteúdo solto, **só o quiz é persistido**: livro de perguntas com sala ao vivo. Tabela `quizzes` (`id`, `titulo`, `descricao`, `perguntas` JSON, `createdAt`, `updatedAt`); partida, jogadores e ranking **nunca** vão ao banco. Mesmo padrão dos outros conteúdos (`requerSessao` no load/action, `Pagina`/`CabecalhoPagina`, `CardConteudo` na lista)

- **Tempo real por polling (~1s), sala em memória** (`$lib/server/quiz-sala.ts`): `Sala` num `Map` pendurado em `globalThis.__mcursoQuizSalas` (sobrevive ao HMR do Vite). Não há timer de fundo: o auto-avanço é resolvido de forma preguiçosa em `avancarSala(sala, agora)`, chamado a cada leitura/polling e antes de aceitar resposta. Processo único (adapter-node); reiniciar o servidor apaga as salas, o que é aceito de propósito. Salas sem movimento por 6h somem na próxima criação
- **Fases**: `lobby` → `pergunta` → `revelacao` → (`pergunta` …) → `fim`. Pergunta vira revelação quando o tempo acaba **ou** todos responderam; a revelação espera `ESPERA_REVELACAO_MS = 4000` e avança sozinha. O professor também controla na mão (`iniciar` no lobby, `proxima` na pergunta/revelação) e tem duas saídas: **`encerrar`** ("Encerrar o quiz" — marca `sala.encerrada`: fecha novas entradas e a partida segue normal para quem já está, até o ranking) e **`sair`** ("Sair e remover todos", com `confirm()` — apaga a sala da memória na hora e todo aluno cai em "Sala não encontrada"). `entrarSala` recusa sala `encerrada`/`fim` ("já foi encerrado") além da já começada; `iniciar` continua permitido com a sala encerrada (os que estão no lobby ainda jogam). Código de 6 caracteres sem O/0/I/1 (`ALFABETO_CODIGO`), lido em voz alta
- **O gabarito não sai do servidor durante a pergunta**: `perguntaEmJogo()` devolve `correta: null` até a revelação (`status === 'revelacao' || 'fim'`), valendo para host e aluno
- **Pontuação Kahoot**: `pontosDaResposta()` dá de 500 a `PONTOS_BASE = 1000` conforme o tempo que sobrou; erro/omissão é zero. `calcularRanking()` ordena por pontuação (nome como desempate), quem empata **divide a posição** (1, 1, 3) e o ranking final mostra **acertos e erros por aluno** (`erros = resolvidas − acertos`; pergunta em branco conta como erro), com badge da contagem no ranking do professor e no top 5 do aluno
- **API** (`src/routes/api/quiz/sala/[codigo]/+server.ts`): o `GET` é o polling (host se `locals.session`, aluno se `?j=<id>`; `cache-control: no-store`) e o `POST` recebe JSON `{ acao: 'iniciar' | 'proxima' | 'responder', jogadorId?, indice? }`. O **aluno responde por `fetch` POST**, não por form action: uma action `?/x` substituiria a query e perderia o `?j=` que identifica o jogador. O cliente usa `$lib/quiz-cliente.ts` (`buscarEstado`/`enviarAcao`)
- **Contador no cliente por diferença**: o servidor manda `tempoRestanteMs` no momento da resposta e o cliente recomputa com o próprio relógio (guarda `recebidoEm`), sem depender de os relógios baterem
- **Editor** (`$lib/components/EditorQuiz.svelte`): título/descrição, cartões de pergunta (2–4 alternativas com rádio da correta, tempo 5–120s), e um `<details>` para **colar um JSON pronto** (`interpretarQuizImportado` aceita `{ titulo?, descricao?, perguntas }` ou array direto, com apelidos de campo e alternativa como string ou `{ texto, correta }`). O rádio da alternativa usa `name` por pergunta. Ao lado de "Importar perguntas" há **"Exportar perguntas"**, que joga o quiz atual (título, descrição e perguntas, **sem `id`** — o parser gera ids novos) no mesmo textarea, então dá para copiar/guardar/reimportar
- `$lib/quiz.ts` é client-safe (tipos, constantes, normalização `normalizarPergunta(s)`, validação `validarPerguntas`, pontuação, ranking, parser de importação e path helpers `caminhoEditarQuiz`/`caminhoHost`/`caminhoJogar`); `$lib/server/quiz.ts` é o CRUD. Rotas: lista `/quiz`, edição `/quiz/[quizId]/editar`, host `/quiz/host/[codigo]` (exige sessão), aluno em `/quiz/jogar` (código + nome, público) e `/quiz/jogar/[codigo]?j=<id>`
- **Navbar**: sem sessão (visão do aluno) o menu mostra "Entrar no quiz" → `/quiz/jogar`, para não precisar digitar a URL; com sessão seguem os links de gestão (Apostilas/Anexos/Atividades/Quiz). O `Navbar` decide por `data.user` do `+layout.server.ts`

### Importação/exportação por JSON (`/importar`)

Parser client-safe em `src/lib/importar.ts` (`interpretarImportacao`/`resumoImportacao`/`EXEMPLOS_IMPORTACAO`, contrato canônico em `DOCS/importacao-ia.md`) e import transacional em `src/lib/server/importar.ts`, tudo na rota `/importar` (link na Navbar)

- Apostila importada **sempre cria nova**; bloco vazio é **mantido e avisado** (pendências em `src/lib/blocos-pendentes.ts`, banner no `EditorConteudo` em modo edição — nunca em leitura)
- Link interno entra como `alvoTitulo` (aula resolve na própria apostila; anexo/atividade por conteúdo existente)
- **`aula` NÃO é importável individualmente** (envelope individual é só `anexo`/`exercicio`/`quiz`)
- Export round-trip na mesma rota: `exportarApostilaJson`/`exportarSoltoJson`/`exportarQuizJson` convertem links de volta para `alvoTitulo`; apostila **sem aula não aparece** na lista de exportação (`selectDistinct` sobre `aulas`)
- Inserções em tx são síncronas (sem `Promise.all` dentro da tx)
- Um botão por tipo (**Apostila/Anexo/Atividade/Quiz**) abre um **popup com um exemplo completo** para copiar para a IA: a apostila exemplo cobre os 12 tipos de bloco; o botão "Usar no editor" preenche o textarea e fecha
- Tabela na exportação: `tabelaParaExportar` escolhe o formato curto (`cabeçalho` + `linhas`) quando a tabela é simples e o canônico quando tem mescla, legenda, zebra, `th` avulso, alinhamento, coluna de cabeçalho ou mais de uma linha de cabeçalho; os dois voltam pelo mesmo `lerTabela`
- Armadilhas: as chaves de `exportaveis` no `load` são **singulares** (`apostila`/`anexo`/`exercicio`/`quiz` — bug 500 no SSR por `exportaveis.apostilas` vs `[tipoExport]`); o `.modal-box` da lib **não** tem `onclick` — o fechamento por fundo é `event.target === event.currentTarget` no wrapper, e o `role="dialog"`/`tabindex="-1"`/Escape são o que mantém o `svelte-check` em 0 avisos

### Blocos de conteúdo

JSON em coluna, não tabela filha. Os 12 tipos: texto, título, código, mermaid, imagem, tabela, fórmula, link, exercício, dissertativa, simulação e html. `exercicio`, `dissertativa`, `simulacao`, `html` e `tabela` editam dentro do próprio card (`EM_CARTAO` no `EditorCanvas`), sem camada de configuração

- **O bloco `titulo` vai de H1 a H6 e o nível é escolhido por botões, não por `select`**: `NIVEIS_TITULO` em `blocks.ts` é a lista válida (o tipo `NivelTitulo` vem dela e `ehNivelTitulo` valida o que vem do POST; fora da lista o bloco é descartado). ### Uploads

**Uploads (imagens/anexos) são arquivo em disco, nunca no banco**: o conteúdo guarda só a URL `/uploads/<uuid>.<ext>` e o arquivo fica em `UPLOADS_DIR`. A política mora num lugar só (`src/lib/server/uploads.ts`): `EXTS_PERMITIDAS` (`png jpg jpeg webp gif svg pdf txt md`), `LIMITE_UPLOAD_BYTES` (10 MB) e `conferirUploads` (resolve a pasta e monta os avisos do boot)

- **A leitura é pública** — `/uploads/[...caminho]` não exige sessão, porque leitura/impressão/apresentação são públicas e, exigindo login, toda imagem saía quebrada para o aluno; o nome é UUID (não enumerável) e o arquivo nunca muda depois de gravado, então sai com `cache-control: immutable` e vem por **stream** (não `readFileSync`), e o SVG (único da lista que pode trazer script) sai com `content-security-policy: sandbox`
- **A escrita continua só com sessão** (`POST /api/upload`, que confere extensão e tamanho e responde JSON legível)
- `UPLOADS_DIR` precisa ser **absoluto** em produção, fora da pasta do app — o boot loga o caminho resolvido e **avisa** quando é relativo fora do dev
- O `BODY_SIZE_LIMIT` do adapter-node (default **512K**!) corta o corpo **antes** da rota, então uma foto de 1 MB falha com 413 e a mensagem amigável do app nem roda — o boot avisa quando o corte é menor que o limite do app e o valor documentado é `12M`
- O `POST` **não** confere o `content-length` antes de ler o corpo: responder 413 sem consumir o multipart deixa o navegador ainda enviando e o `fetch` morre com `ERR_CONNECTION_RESET` ("Failed to fetch") em vez de mostrar a mensagem — o cliente `undici` tolera e mente que funciona, o Chrome não. Quem corta corpo absurdo é o `BODY_SIZE_LIMIT` e a mensagem amigável vem da checagem do arquivo
- Limitações aceitas: sem limpeza de órfãos (apagar o bloco não apaga o arquivo), sem dedupe e o nome original se perde

## ahmardesign — regras (da doc da lib, não óbvias)

- **A lib é a fonte da verdade da UI**: construir com as classes do `ahmardesign` (`btn`, `card`, `select`, `alert`, `tabs`, utilitários de flex/gap/spacing/radius…). Antes de escrever qualquer estilo, verificar se a lib já não resolve — não recriar componentes nem aparência da lib no app
- **CSS local (`<style>` no Svelte) precisa ser justificado**: só quando a lib não tem o que precisa, e no mínimo possível. Nunca estilizar por convenience/ajuste fino o que a lib já cobre
- **Nunca hardcodar o que o tema muda** (raio, cor, espaçamento): usar os tokens/classes do tema, senão o layout quebra em temas quadrados como `brutalist` (`--rounded-box: 0px`). Ex.: raio → classes `.rounded-box`/`.rounded-btn`/`.rounded-badge` ou `var(--rounded-box)`; no CSS local, preferir a classe da lib
- **A lib vem do registry** (`^1.2.0` no package.json) para o deploy funcionar em qualquer host. Mudança na lib local só entra no app depois de `npm publish` + `npm install`; para developar contra o fonte, dá pra apontar temporariamente para `link:../ahmardesign` (symlink/junction) e voltar para `^x.y.z` antes de publicar
- CSS importa no servidor normalmente: `@ahmartecnologias/ahmardesign/ahmardesign.css` via subcaminho do package `exports`
- **O helper JS (`.../ahmardesign.js`) SÓ no cliente** — executa `AHMAR.init()` na carga e acessa `document.body`/`localStorage`: usar import dinâmico em `onMount`, nunca no SSR
- Tema via `data-theme` no `<body>`; `AHMAR.setTheme()`; evento `ahmar-theme-change` no `window` para sincronizar store Svelte
- **Tema sem flash (FOUC)**: o SSR sempre emite `data-theme="brutalist"`, então o `app.html` tem um `<script>` síncrono no início do `<body>` que aplica a chave `ahmar-theme` do localStorage antes de `%sveltekit.body%`. Consequências: a chave é a da lib (`ahmar-theme`, não uma própria) e a lista de temas válidos é duplicada no script — `src/lib/theme.test.ts` falha se as duas divergirem. Também importa aplicar `iniciarTema()` **antes** de `AHMAR.init()`, senão o `initTheme()` da lib cai no `light` e troca o tema depois da primeira pintura
- Componentes **não têm margem padrão**: usar `gap` (flex/grid) **ou** `.space-y-*` (irmãos não-flex), nunca os dois juntos no mesmo container
- `AHMAR.init()` é idempotente — chamar no mount cobre elementos renderizados depois (`{#if}`, blocos dinâmicos)

## Componentes de UI

- **`DOCS/componentes-ui.md` é a fonte da verdade do que já foi extraído**: plano priorizado (P0–P3) com colunas de status (`⬜`/`🚧`/`✅`) e as ocorrências a unificar. **Ao criar um componente, marcar o status e a data lá** — não confiar em memória nem em commit antigo

- **Nada de wrapper para o que já é classe da lib** (`alert`, `card`, `modal`, `table`, `tabs`, `btn`, utilitários de flex/gap). Se a inconsistência é de *classe*, padroniza-se a classe, não se cria componente

- **As ações do `CabecalhoPagina` ficam na mesma linha, à direita**: o header é `flex flex-nowrap` com a coluna de título `min-w-0 flex-1` (`h1` com `break-words`) e o grupo de ações `ml-auto flex shrink-0` — com descrição longa (ou título sem espaços) o botão nunca cai para a linha de baixo nem é empurrado à esquerda. O `e2e/visao.spec.ts` mede a borda direita do botão contra a borda do conteúdo **e** que o `y` do botão casa com o `y` do título (±8px)
- **Rótulo de ação é contrato de E2E**: "Imprimir/PDF" (link de contexto), "Imprimir / salvar PDF" (página de impressão), "Imprimir / PDF" (cartão de resultado), "Apresentar" e "Visualizar" estão fixados em specs e viraram constante em `$lib/conteudo.ts`. **São três strings de impressão diferentes** — reaproveitar a constante errada quebra o E2E sem erro de tipo. Ao extrair, **reusar a string existente**, nunca renomear
- **`Campo` com `extra` não usa `.label`**: o padding horizontal da lib empurra o controle extra 8px para dentro e ele desalinha da borda do campo (`fluxo.spec.ts` mede isso no tema do Mermaid). Com `extra` a linha do rótulo é flex puro
- **Badge que divide a linha com texto que pode ser longo leva `shrink-0`** (`Alternativa.svelte`, `DataBadge`, e os badges das alternativas no `host`/`jogar` do quiz): o `.btn` da lib é `inline-flex` **sem** `flex-wrap`, então um badge flex item com o `flex-shrink: 1` default encolhe até o min-content e o texto dele **quebra em duas linhas**, estourando a altura fixa de `1.25rem` do `.badge` (o caso do "sua resposta" com alternativa comprida). A badge fica com o tamanho do texto dela; quem cede espaço é o texto da alternativa, que já é `whitespace-normal`
- **Busca por título é padrão das quatro listagens** (home/apostilas, painel da apostila, anexos e atividades): input `type="search"` na barra de contagem, `aria-label` "Buscar X por título". O filtro mora onde a lista nasce — state interno `$state`/`$derived` na home e no painel, e dentro do `PainelSoltos` (sem props `busca`/`aoBuscar`). **Duas contagens**: o total real decide a mensagem de vazio (`rotuloVazio`) e o filtrado decide a contagem + o alert "Nada encontrado para X" — o bug antigo era só ter a lista já filtrada, aí o alert nunca disparava. No painel da apostila a busca **esconde a alça de arrasto** e `moverAula` tem guarda `if (busca.trim()) return` (salvar a ordem por uma lista filtrada salvaria só o pedaço visível); o agrupamento usa `visiveis`, não a lista real. Rótulo de criação padronizado como `+ Nome` (texto, não ícone — o `getByRole` do Playwright casa por substring, então os rótulos sem `+` seguem válidos)
- **Lista de conteúdo é sempre `CardConteudo`** (as quatro: apostilas na home, aulas no painel, anexos e atividades), com a barra de contagem à esquerda e o `SeletorVisao` à direita. O cartão **sem ações** é `<a>` (o cartão inteiro é o link, como na home) e **com ações** é `<li>`, porque botão dentro de link é HTML inválido — daí o container ser `div` na home e `ul` nos painéis, e o `li` do painel solto ser contrato de E2E. O cartão de aula no painel **não é link** (checar com `toContainText`, não `toHaveAttribute('href')`). A **alça de arrasto** fica no **rodapé do cartão, à esquerda das ações** — o `CardConteudo.svelte` renderiza `{#if alca || acoes}` numa linha só. A classe do container vem de `classeLista()` em `src/lib/visao.svelte.ts` (`space-y-2` → `grid gap-4 sm:grid-cols-2`) e `ul` aceita `display: grid`, então o container não muda entre os modos. A visão é **uma preferência só do navegador** (`mcurso:visao`, lida por `iniciarVisao()` no mount do `+layout.svelte`, sem FOUC e sem script no `app.html`), compartilhada por aluno e professor — a home é pública, então ela não pode depender da sessão. Snippet que preenche a prop `acoes`/`marcadores` do `PainelSoltos` precisa vir por um apelido (`acoesItem = $derived(acoes)`), senão o `{#snippet acoes()}` é auto-referência
- **Submissão de form é sempre `use:enviando`** (`src/lib/enviando.ts`): toda submissão POST passa por essa action, que embute o `enhance` e, enquanto a action roda, põe `disabled` + `btn loading` (classe da lib) + `aria-busy` em todos os `button[type="submit"]` do form. Os 20 usos cobrem todos os forms POST do app. Opções: `confirmar?: () => boolean`, `sucesso?: (resultado) => void`, `aoResultado?: (ctx) => void`. Quatro decisões travadas: (1) **o `confirm()` de exclusão passa por `confirmar`, nunca por `onsubmit`** — o `handle_submit` do `enhance` sempre chama `event.preventDefault()` e não olha `event.defaultPrevented`, e o listener direto dele roda antes do `onsubmit` delegado do Svelte, então o confirm no `onsubmit` rodaria com o fetch já em voo; `confirmar` devolvendo `false` chama `cancel()` (sem fetch e sem `ligar`); (2) no sucesso chama **`invalidateAll()` antes do `applyAction`** (é o que o `fallback_callback` do `enhance` faz: reseta o form + invalida os loads) — esquecer isso foi o bug que derrubou 8 E2E, porque o POST voltava 200, o botão saía do `loading` e a lista de `data` (anexos, seções, aulas) ficava velha; (3) `aoResultado` trata o resultado **sem `applyAction`** e só existe no exportar do `/importar` (preserva o comportamento antigo de não mexer nos selects); (4) o `enhance` troca o reload síncrono por fetch + navegação client-side, então **E2E que clica "Entrar"/"Criar" e já navega precisa esperar** a navegação assentar. Feedback de fetch fora de form (salvar a ordem, host e jogador do quiz) usa estados locais (`salvandoOrdem`, `comandoEmAndamento`, `alternativaEnviada`)

## Convenções de teste

- **E2E roda contra um banco compartilhado pelas specs**: título de conteúdo criado em teste leva token `Date.now()` (contagem absoluta na home é frágil) e o teste casa por substring (`getByRole(..., { exact: false })`)
- **`hasText` é substring case-insensitive**: para casar texto exato dentro de um locator composto, usar `filter({ has: getByText(..., { exact: true }) })` (gráfico da função afim casa com Função afim)
- **Campo de formulário não se lê com `toHaveText`**: ler o `value` (`evaluateAll` + `expect.poll`; `toHaveValues` é assertion de `<select multiple>`)
- **Depois de clicar "Entrar"/"Criar", esperar a navegação assentar** antes de assertar URL/conteúdo (o `enhance` navega client-side; quem não espera cai no `/login` ou lê a página antiga)
- **O título da apostila no painel logado é um `TextoEditavel`** com `aria-label`: o E2E casa por papel `heading level 1` + `toContainText`, não por nome acessível
- **Simulação: medir antes da troca de biblioteca dá leitura velha** — os 700 ms de debounce significam que, logo após `selectOption('q5')`, a moldura do p5 ainda está na tela. O E2E do q5 exige `Q5.instances.length > 0` (o construtor não morreu) **e** `buffer >= largura` dentro do `poll`; `expect([data-simulacao-erro]).toHaveCount(0)` sozinho passa com o q5 quebrado
- **Quiz: alternativa longa não pode quebrar o badge** ("sua resposta" com `shrink-0`): o `quiz.spec.ts` mede as *line boxes* do badge com `Range.getClientRects()` em tela de 390px
- **Popup de exemplo do `/importar`**: modal com `role="dialog"`, fechamento por backdrop (`event.target === event.currentTarget` no wrapper — o `.modal-box` da lib não tem `onclick`)/Escape, "Copiar para a IA" com feedback "Copiado!" e fallback `execCommand`
- **Atividade precisa de bloco de exercício/dissertativa para salvar** (`fail(400)`): o teste cria uma dissertativa antes de salvar

## Integrações com quirks conhecidos

- Better Auth no SvelteKit precisa `basePath: '/api/auth'` na inicialização do `auth.ts`; o `src/hooks.server.ts` resolve a sessão **antes** de cada request e põe em `event.locals`, e o `svelteKitHandler` ainda atende `/api/auth/*`
- `src/lib/server/auth-cli.ts` (+ `auth-cli-mysql.ts`) é config mínima do Better Auth usada **só** pelo CLI (`@better-auth/cli`) para gerar os auth-schemas; não é o auth do runtime. O CLI escolhe o dialeto pelo `provider` do adapter e é a fonte da verdade dos auth-schemas (por isso `auth-schema.mysql.ts` usa `timestamp(3)` e `varchar(36)`/`varchar(255)` nas PKs e campos indexáveis — TEXT não é indexável no MySQL); o `@better-auth/cli` foi validado antes de usar (regenerar o `auth-schema.ts` reproduz o commitado byte a byte; o warning "Drizzle schema mismatch" e o `ECONNREFUSED` do MySQL na geração são inofensivos)
- Mermaid roda em SSR? Não — renderizar no cliente (blocos mermaid são típicos candidatos a componente `{#if}`/lazy no SvelteKit)
- Tema do Mermaid é **por bloco** (`tema` em `BlocoMermaid`, default `neutral`, lista em `TEMAS_MERMAID`): muda só `mermaid.initialize({ theme })` e o `$effect` do `Mermaid.svelte` re-renderiza. Valor vindo do POST é saneado em `normalizarCamposBloco` — bloco antigo sem o campo ou com tema fora da lista cai no default, nunca é descartado (o bloco inteiro tem mais valor que o cosmético)
- adapter-node: dependência em `dependencies` fica **externa** no build (resolvida de `node_modules` em runtime); em `devDependencies` é **bundlada**. Por isso o SO do runtime só enxerga `dependencies` — é a regra do package.json (`ssr.external`/`rollupOptions.external` no vite não funcionam; rolldown ignora). **O app não tem nenhuma dependência nativa**: o SQLite vem do `node:sqlite` do Node ≥ 22.13 (`engines.node`) e o MySQL usa o `mysql2` (JS puro). `p5` e `q5` ficam em `dependencies` pelo mesmo motivo (a rota `/lib/[...caminho]` lê do `node_modules` em runtime)
- **Sem better-sqlite3 (decisão de 12/10/2026, após três deploys quebrados na Hostinger)**: o container do host é antigo (glibc < 2.29, Python 3.6) e nenhum binário do better-sqlite3 carrega lá — 13.x traz prebuild exigindo **GLIBC_2.29**, o prebuild da 12.x baixado pelo `prebuild-install` também, e o fallback de compilação morre no Python 3.6 (o gyp moderno precisa de 3.8+). Por isso o SQLite é o **`node:sqlite`** (`DatabaseSync`), embutido no Node (zero binário no install e no runtime): o app passa o `DatabaseSync` **direto no driver `better-sqlite3` do drizzle** com shims em `src/lib/server/db/node-sqlite.ts` (a session do driver só usa `prepare().all/get/run`, `prepare().raw().all/get` e `transaction(fn)`). O `DatabaseSync` liga FK por padrão (o better-sqlite3 deixava desligado), então abrimos com `enableForeignKeyConstraints: false` + `PRAGMA journal_mode = WAL`. O `import Client from 'better-sqlite3'` do driver é satisfeito por um **stub `file:`** em `vendor/better-sqlite3-stub` (7.99.0, só para o peer `>=7` do drizzle; nunca instanciado). `@types/better-sqlite3` fica em devDependencies só pelas tipagens. Efeitos: `npm run db:migrate` manual (drizzle-kit) pode não funcionar sem o pacote real — o app migra no boot, então não faz falta; `db:generate` segue ok (não conecta no banco)
- **npm 11+ não precisa de configurações especiais de build**: ao contrário da pnpm 11+ (que exigia `allowBuilds`/`strictDepBuilds` no `pnpm-workspace.yaml` — arquivo removido na migração), o npm não requer mapa de builds; o `postinstall` do package.json roda o `svelte-kit sync`
- **`overrides` do `cookie` REMOVIDO em 12/10/2026 por decisão** (pedido de simplificação): o `@sveltejs/kit` 2.x segue declarando `cookie: ^0.6.0`, então o advisory GHSA-pxg6-pf52-xh8x voltou ao `npm audit`. Risco baixo num app single-user; se um dia quiser zerar o audit, restaurar `overrides: { cookie: ^0.7.2 }` no `package.json`
- Sobram **3 advisories** no `npm audit` (1 moderado + 2 low), todos **aceitos de propósito**: o moderado é `esbuild <=0.24.2` via `drizzle-kit > @esbuild-kit/esm-loader` (devDependency; advisory é do `esbuild --serve`, que nunca rodamos; forçar 0.25 no loader pinado arrisca quebrar `db:generate` — reavaliar quando o drizzle-kit trocar o loader); os 2 low são **`cookie`** (ver acima) e **`katex`** via `mermaid` (pré-existente)
- **Transação: um corpo só, `async`, nos dois dialetos** (`transacao()` em `src/lib/server/db/transacao.ts`) — é o ponto único que o dialeto troca. No SQLite o shim de `node-sqlite.ts` **fecha a transação quando o promise assenta** (COMMIT no resolve, ROLLBACK no reject; um `desfazer` tolera o rollback já feito). Consequência que não pode ser esquecida: **o corpo de uma transação não pode fazer I/O de verdade** — só consultas ao `db` e código puro, porque cada `await` resolve em microtask e a transação nunca devolve o controle ao event loop (se devolvesse, outra request entraria na mesma transação). O drizzle com o `node:sqlite` continua síncrono por baixo; os corpos ficam nos serviços de `lib/server` (`apostila.ts`, `importar.ts`), nunca nas rotas
- **MySQL/MariaDB**: três coisas que só aparecem rodando de verdade — (1) **a tabela carrega o mapa de valores** (ver "Modelo de dados"), então `db/tabelas.ts` tem que ser a fonte das consultas; (2) **insert no MySQL não tem `.returning()`** (o drizzle só expõe `$returningId()` — e devolve vazio se a coluna não for PK autoincremento), então todo insert passa por `inserirId` em `db/inserir.ts`; o `RETURNING` de `update`/`delete` **não** foi mexido (o MariaDB suporta); (3) `datetime`/`timestamp` do drizzle fazem round-trip em UTC (`toISOString` na escrita, `+0000`/`Z` na leitura), simétrico com o `mode: 'timestamp'` (epoch) do SQLite — a única diferença é o `timestamp(3)` do auth-schema.mysql, que fica como está (ver o bullet do CLI). O `json()` devolve objeto/array pelo próprio `mysql2` (o app já consome com cast) e a conexão é um **pool** (ver abaixo)
- **A conexão MySQL é um pool, nunca `createConnection`** (o deploy de 18/10/2026 subiu e ficou em 500 em tudo por causa disso): em hospedagem compartilhada o servidor derruba a conexão parada no `wait_timeout` e, numa conexão única, ela **nunca** volta — a partir daí toda consulta falha com `Failed query: ...` e o app só se recupera reiniciando o processo. O pool (`mysql.createPool({ uri, connectionLimit: 10, maxIdle: 2, idleTimeout: 60_000, enableKeepAlive: true, ... })`) descarta a conexão morta assim que o socket fecha e abre outra na consulta seguinte. Reproduzido local com `kill <id>` no servidor: com `createConnection` o app dá 500 **para sempre**; com o pool a requisição seguinte já responde 200. As transações seguem numa conexão só — o `db.transaction` do drizzle pega uma conexão dedicada do pool e devolve no fim (`transacao.ts` não mudou)
- **Migration no boot, não no deploy**: `aplicarMigrations(db, dialeto)` roda dentro de `db/index.ts`, importado por `auth.ts` → `hooks.server.ts` no boot, antes de qualquer consulta. Não usar `drizzle-kit migrate` no servidor (é devDependency e a Hostinger pode instalar só `dependencies`). A pasta é **por dialeto** (`PASTAS` em `migrar.ts`: `drizzle`/`drizzle-mysql`, a cópia em `build/`, a original do checkout em `../`, e `MIGRATIONS_DIR` na frente de tudo) e o `npm run build` copia as duas para dentro de `build/`
- **O boot confere que a migração criou tabelas** (`contarTabelas`/`conferirTabelas` em `db/index.ts` e `migrar.ts`): `__drizzle_migrations` pode registrar tudo como migrado num banco **sem tabela nenhuma** (controle sobrado de um banco recriado) — o drizzle então pula tudo em silêncio, o log mente "banco em dia" e toda consulta falha com `ER_NO_SUCH_TABLE`. Agora o log traz a contagem (`— 11 tabela(s)`) e, se o banco só tem o controle de migração, o boot **falha com a instrução** (apagar `__drizzle_migrations` e subir de novo) em vez de servir 500
- **O 500 do servidor loga a causa** (`handleError` em `hooks.server.ts`): o log padrão do SvelteKit mostra só o erro de fora, e o do drizzle sai como `Failed query: ...`, escondendo o código do MySQL (`PROTOCOL_CONNECTION_LOST`, `ER_NO_SUCH_TABLE`, `ER_ACCESS_DENIED`...) que é o que diz o que aconteceu. O `handleError` loga o erro **e** `error.cause`
- **O build fala com o banco**: o `analyse` do pós-build do SvelteKit **importa o módulo do servidor**, então o `vite build` abre a conexão e roda as migrations (um banco MySQL vazio virou **11 tabelas só com o build**, sem `node build`). Três consequências: (1) com `DB_DIALECT=mysql` o banco precisa **existir antes do build** (senão `ER_BAD_DB_ERROR` e o build morre) e o usuário precisa de **DDL no build e no boot**; (2) por isso o `webServer` do E2E faz o reset **antes** do build (é quem cria o banco); (3) no deploy, criar o banco no painel **antes** de subir o código. Não "consertar" tornando o `db/index.ts` preguiçoso: todas as consultas importam `db`/`tabelas` no topo, o custo não compensa
- **Trocar um deploy para MySQL é só ambiente, nunca código** (o `.env` é **gitignored** — `.env`/`.env.*`, com `!.env.example` —, então o push não leva variável nenhuma e o `.env` de produção segue como estava; o que está versionado é só o modelo). O dialeto é lido de `DB_DIALECT` no `db/index.ts`. Armadilhas que já apareceram: a comparação é **exata** (`mysql` minúsculo; `MySQL` cai em SQLite **em silêncio**), sem `DB_URL` o boot **falha de propósito** (mensagem clara) em vez de cair no SQLite, o usuário do banco precisa de **DDL** e o banco deve nascer **`utf8mb4`/`utf8mb4_unicode_ci`** (Hostinger confirmada: MariaDB 11.8; o app **não tem `LIKE` em SQL** — a busca por título é filtro de tela —, então a collation afeta ordenação, não busca). `DB_PATH` pode ficar no `.env` (ignorado no modo mysql): o **rollback é uma linha** — apagar/comentar o `DB_DIALECT` volta para o SQLite velho, intacto
- `DB_PATH`/`UPLOADS_DIR` em produção precisam estar **fora da pasta de build**: host com build versionado (Hostinger) apaga a pasta a cada deploy. No MySQL o que precisa sobreviver é o **banco em si** (`DB_URL`) — não há arquivo no deploy; **`UPLOADS_DIR` continua sendo arquivo mesmo no MySQL**: o backup gerenciado do banco **não** cobre os uploads, que precisam do backup próprio. Na Hostinger a área é `hbuilds/versions/<build-id>/` (só as **2 últimas** versões guardadas) e `hbuilds/`/`public_html` são **sobrescritos a cada deploy** — edição manual por File Manager/FTP/SSH **não persiste**, e trocar o deploy para manual não salva um caminho relativo: o que salva é o caminho absoluto fora dessa área (ex.: `/home/uXXXXXXXX/mcurso/uploads`), com backup próprio
- Arrasto de listas é genérico em `src/lib/arrastar.ts`: o item usa `{@attach arrastar(opcoes)}` e o container `data-arrasto-lista={grupo}`; `data-arrasto-item` marca cada item e `data-arrasto-alca` a alça (o arrasto só começa nela, para não sequestrar seleção/caret do `TextoEditavel`). `moverItem` faz o splice local e as classes `.arrastando`/`.arrasto-alvo(-fim)` vivem no `app.css` (a lib não tem estilo de arrasto)
