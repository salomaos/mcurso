# mcurso

App pessoal (single user) para criar e gerenciar apostilas de aula. UI, código e commits em pt-BR. **`main` é produção, `dev` é onde se trabalha** (ver "Git"), commits com Conventional Commits.

## Git: o commit é do usuário, nunca do agente

**Nunca rode `git commit` nem `git push` por conta própria.** O agente implementa, roda `pnpm check`/`pnpm test`/E2E, e **para**: mostra o que mudou (arquivos e pontos de decisão) e espera o usuário revisar e pedir o commit ("pode commitar"). Só então commita — e o push, se pedido junto ou depois. Vale mesmo com os testes verdes e a mudança "obviamente" pronta: a revisão do diff pelo usuário é parte do fluxo, não uma etapa opcional. Vale também para mudança pequena, documentação, correção de typo e commit de teste — nada de "já que estava ali".

## Git: `main` é produção, `dev` é onde se trabalha

- **`main` é a branch publicada** e é a **branch conectada no deploy da Hostinger**: o auto-deploy dispara no *push* para a branch conectada (hPanel → Deploy → Deployment settings → Branch), então push na `main` = subir para o ar.
- **`dev` é o trabalho do dia a dia** (`feature/*` quando a mudança for grande). Nada entra na `main` por push direto: entra por **pull request**.
- Quem exige o PR é a **ruleset do GitHub** (Settings → Rules → Rulesets, alvo `main`): *Require a pull request before merging* (**0 aprovações** — quem abre o PR mergeia o próprio), *Block force pushes* e *Restrict deletions*, **sem bypass**. Ela vale de graça porque **o repo é público** (ruleset em repo privado exigiria GitHub Pro) e é do lado do servidor: pega o terminal e o agente, sem depender de disciplina.
- **Fluxo**: commit na `dev` → push da `dev` → PR `dev` → `main` → merge → **o merge dispara o deploy**. Commitar e pushar na `dev` não sobe nada. Se a ruleset cair por algum motivo (plano, repo virar privado), o mínimo continua sendo **nunca push direto na `main`**.

## Stack (decisões acordadas)

- **SvelteKit 2 / Svelte 5** + **adapter-node** (SSR/Node). O `vite.config.ts` força **runes mode** em todo o app (`runes: true` para tudo fora de `node_modules`): componente novo já nasce com `$state`/`$derived`/`$props`/`$effect`, sem `export let`/`$:` legado. Scaffold: `pnpm create sv@latest`
- Node 24, **pnpm**
- **Drizzle ORM** com **SQLite** (dev) ou **MySQL/MariaDB** (hospedagem), **escolhido por deploy** com `DB_DIALECT=sqlite|mysql` — não é escolha de runtime, é de ambiente. No SQLite o driver é o `node:sqlite` do Node ≥ 22.13 (**sem binário nativo** — o `better-sqlite3` não carrega na glibc da Hostinger; ver quirks): o driver `better-sqlite3` do drizzle estável é alimentado por um `DatabaseSync` com shims em `src/lib/server/db/node-sqlite.ts`. No MySQL o driver é o `mysql2` (JS puro). Migrations geradas com `drizzle-kit` e **aplicadas no boot do app** (`db/migrar.ts`), não por passo separado de deploy — `drizzle/` no SQLite, `drizzle-mysql/` no MySQL. Os dois schemas vivem lado a lado (`schema.ts`/`schema.mysql.ts` e os dois auth-schemas), com o `schema-paridade.test.ts` guardando o contrato. PostgreSQL está descartado.
- **Better Auth** com adapter Drizzle; login por **senha mestra** — usuário único professor, sem registro/2FA
- CSS: **`@ahmartecnologias/ahmardesign`** (Vanilla CSS). Tema padrão `brutalist` + seletor de tema
- Diagramas: **Mermaid**. Código: **highlight.js**. Fórmulas: **KaTeX** (adicionado quando necessário)
- Testes: **Vitest** (unit/integration) + **Playwright** (E2E)

Para um subconjunto, passe as specs: `pnpm exec playwright test e2e/fluxo.spec.ts e2e/quiz.spec.ts`

  - **A mesma suíte roda no MySQL/MariaDB**: com o banco local de pé (`docker compose up -d`, porta 3307), basta `E2E_DIALECT=mysql` — o `E2E_DB_URL` default (`e2e/ambiente.ts`) já aponta para `mysql://root:mcurso@127.0.0.1:3307/mcurso_e2e`. Para outro servidor, `E2E_DB_URL=mysql://root:senha@host:3306/mcurso_e2e` (o banco precisa terminar em `_e2e` — é a trava do reset contra apagar um banco de verdade — e o usuário precisa poder criar/apagar bancos: o reset faz `drop`/`create`). É essa execução que prova o dialeto de ponta a ponta; 96/96 nos dois. Env var de shell **não** sobrevive entre comandos: passe as duas no mesmo comando
  - Para iterar rápido, sobe o servidor à mão contra o banco descartável e deixa o Playwright **reaproveitar** (`reuseExistingServer` já é ligado fora de CI): assim cada rodada de specs custa segundos em vez do build de cada vez. Buildar uma vez, `node scripts/e2e-reset.mjs` com o `DB_DIALECT` do alvo, subir `node build` com o mesmo `env` do `webServer` (porta 5179) e rodar as specs
- `pnpm check` sai **0 erros / 0 avisos** com a lib vinda do registry (antes saía 1 só pelos 22 diagnósticos do fonte local do `ahmardesign`, que saiu do caminho)
- Unit (`vitest.config.ts`) só coleta `src/**/*.{test,spec}.{js,ts}` e exclui `e2e/**`, com `environment: 'node'`
- E2E **nunca toca no banco dev**: o `webServer` roda `node scripts/e2e-reset.mjs && pnpm build && node build` (o **reset antes do build** porque o build fala com o banco — ver quirks), recriando o banco de E2E a cada execução — `data/e2e.db` e `data/e2e-uploads` no SQLite, `drop`/`create database` no MySQL (porta 5179, `workers: 1`, `fullyParallel: false`, `retries: 0`). Sem `drizzle-kit migrate`: o app migra sozinho no boot, então o E2E exercita o mesmo caminho do deploy. O banco local é o **`docker compose up -d`** (`docker-compose.yml`: MariaDB **11.8.9**, a mesma versão da hospedagem, porta 3307; root `mcurso`, usuário do app `mcurso`/`mcurso`) e o `E2E_DB_URL` default já aponta para ele. As variáveis vivem em `e2e/ambiente.ts` (banco/credenciais, com `DIALETO_E2E` e `DB_URL_E2E` para o MySQL) e o `env` do `webServer` sobrescreve o `.env` de propósito (`dotenv` não sobrescreve, então nunca usar `process.env.X ?? ...` para isolar)

## Modelo de dados

- **O banco é escolha de deploy (`DB_DIALECT=sqlite|mysql`)** e o código **não ramifica por dialeto** em lugar nenhum, exceto em dois módulos de `src/lib/server/db/`: **`tabelas.ts`** (os objetos de tabela do dialeto em uso — *quem consulta importa daqui*, nunca de `schema.ts`/`schema.mysql.ts`) e **`inserir.ts`** (`inserirId`, o insert que devolve o id gerado). Os dois existem porque o **objeto da tabela carrega o mapa de valores da coluna**: o `mode: 'timestamp'` do SQLite grava segundos e mandava `1792241512` para a coluna `datetime` do MySQL (`Incorrect datetime value`), então usar a tabela do SQLite no driver do MySQL não funciona; e o MySQL **não tem `.returning()`** no builder do insert (o drizzle só oferece `$returningId()`, que devolve a PK pelo `insertId` do driver). O tipo continua sendo o do SQLite (`db` é o drizzle do SQLite; o MySQL entra por cast) — o que muda em runtime é o objeto da tabela e a garantia real vem de rodar a mesma suíte E2E nos dois dialetos

- Apostilas **soltas** (sem hierarquia de curso) organizadas por **aulas/encontros**
- Sessão em `event.locals` via `src/hooks.server.ts` (Better Auth); escrita protegida por `requerSessao()` (`$lib/server/guard.ts`) chamada no load/action — não proteger só o markup
- O usuário professor é criado no primeiro login a partir de `APP_MASTER_EMAIL`/`APP_MASTER_PASSWORD`. Trocar a senha mestra depois **não** remixa o hash guardado: o usuário precisa ser resetado
- **Anexos são soltos**: tabela `anexos` independente, **sem** vínculo de posse com apostila ou aula. O aluno chega neles por link dentro de uma aula; eles não aparecem em listagem de aulas, painel da apostila nem no índice
- Conteúdos (aula/anexo/atividade) compartilham blocos, editor e leitura: usar `src/lib/components/{Editor,Visualizar}Conteudo.svelte` + `src/lib/server/conteudo.ts` (parsing/validação) em vez de duplicar rota/componente. `TipoConteudo` é só conceito de UI
- Rotas de anexo na raiz: `/anexos/[anexoId]` (+ `editar`, `imprimir`, `apresentar`); leitura/impressão/apresentação são públicas, edição e `/anexos` exigem sessão. `caminhoAula()`/`caminhoAnexo()` em `src/lib/conteudo.ts` montam as URLs
- Link interno é genérico: `BlocoLink.alvoId` (+ `tipoLink`, sem `alvoApostilaId`). Link de anexo aponta para `/anexos/[id]` e funciona em qualquer apostila; link de aula precisa da apostila do bloco e o `EditorConteudo` passa o `contexto` ao editor. Picker: `alvosParaLinks()` na aula (aulas da apostila + anexos + atividades) e `alvosAnexos()` no anexo (só anexos). Arquivo externo é `tipoLink: 'externo'`
- **Atividades de exercício** (`/exercicios`) são o terceiro conteúdo solto, montado com os mesmos blocos: a parte pública é diferente de aula/anexo. `TipoConteudo: 'exercicio'` com `ROTULO_TIPO` = "Atividade"; rota pública `/exercicios/[id]`
  - **O gabarito não sai do servidor**: `buscarExercicioPublico()` monta as questões com `questoesPublicas()` (`$lib/corrigir.ts`, que só produz `{id, pergunta, alternativas, selecao}` — sem `correta`/`explicacao`) e a action `?/responder` corrige no POST via `corrigirExercicio()`. Nunca passar o bloco inteiro ao componente `Questao.svelte`
  - **Duas modalidades de escolha**: `BlocoExercicio.selecao` = `radio` (uma correta) ou `checkbox` (várias). `correta` é número no rádio e lista no checkbox; bloco antigo (sem o campo) é rádio. `corretasDoExercicio()` normaliza os dois formatos em lista ordenada (descarta índice fora da faixa, usada por editor, correção e hash) e o `normalizarCamposBloco` grava sempre no formato da modalidade
  - Múltipla escolha exige **conjunto exato**: marcar a certa e mais uma já é errado. No checkbox a resposta chega em `q_<id>` repetido (`form.getAll`), no rádio em um valor só
  - **Dissertativa** é o bloco `dissertativa` (`pergunta` + `orientacao`): resposta aberta, **fora da nota automática** (não conta em `acertos`/`total`). No POST vem em `d_<id>` (limite `LIMITE_DISSERTATIVA`); fora da atividade é só rascunho efêmero. A resposta volta no resultado em `textarea` somente leitura (assim imprime)
  - **Fórmula em alternativa**: o conteúdo entre `$` e `$` (`$lib/matematica.ts` → `TextoMatematico.svelte`) sai com KaTeX, mantendo a alternativa como string só no banco. No PNG do resultado aparece o LaTeX cru (canvas não desenha KaTeX)
  - **Nome do aluno em `sessionStorage`** (`$lib/nome-aluno.ts`, nunca servidor): sobrevive a recarregar e some ao fechar o navegador. Guardar no `oninput`, ler no `onMount` (não existe no SSR)
  - Resultado marca **quais alternativas foram selecionadas** (badge "selecionada" + gabarito) no HTML, no PNG (`[x]`/`[ ]` + "gabarito", para sobreviver a tons de cinza) e no papel
  - Impressão do resultado: botão "Imprimir / PDF" com `window.print()` — sem dependência. `@media print` no `app.css` (`.no-print` esconde botões, `.quebra-pagina` não corta pergunta no meio); `print-color-adjust: exact` é global, então as cores do gabarito saem
  - Sem persistência: o resultado volta no `form` da própria action. Resposta em branco ou índice fora da faixa é zero, não erro (`Number('')` é `0` — descartar string vazia antes)
  - **Chave de integridade** (`$lib/server/chave.ts`): HMAC-SHA256 com `BETTER_AUTH_SECRET` e rótulo de domínio `mcurso:chave-resultado:v1`, formato `base64url(payload).assinatura`. Carrega nome, quando, atividade, apostila/aula, acertos, total e `hashGabarito()` (por questão, os índices corretos unidos com `+`; questões separadas por `|`, ex.: `0+2|1`, e só entra bloco de exercício). É base64, **não criptografia**; a tela de validação (futura) lê e confere a assinatura. Não cobre as respostas discursivas (a chave é da nota)
  - Contexto de origem por `?aula=<id>`: o link de atividade posto dentro de uma aula gera a query (`hrefLinkInterno` com `aulaContexto`), o `BlocoRender`/`VisualizarConteudo` repassam `aulaContexto`. É isso que a chave registra
  - Resultado vira PNG no cliente com Canvas em `$lib/imagem.ts` (sem `html-to-image`, fontes só genéricas, card é texto puro porque `/uploads/*` exige sessão)
  - Atividade em uso não pode ser excluída (409), igual ao anexo; `/exercicios` lista em quais aulas é usada. Atenção ao nome do campo na listagem: `ExercicioUi.discursivas` (sem o "t"), enquanto a correção usa `Correcao.dissertativas` — não padronizar sem mexer nos dois lados
- **Quiz estilo Kahoot** (`/quiz`, quarto conteúdo solto, **só o quiz é persistido**): livro de perguntas de múltipla escolha com sala ao vivo. Tabela `quizzes` (`id`, `titulo`, `descricao`, `perguntas` JSON, `createdAt`, `updatedAt`); partida, jogadores e ranking **nunca** vão ao banco. Mesmo padrão dos outros conteúdos (`requerSessao` no load/action, `Pagina`/`CabecalhoPagina`, `CardConteudo` na lista)
  - **Tempo real por polling (~1s), sala em memória** (`$lib/server/quiz-sala.ts`): `Sala` num `Map` pendurado em `globalThis.__mcursoQuizSalas` (sobrevive ao HMR do Vite). Não há timer de fundo: o auto-avanço é resolvido de forma preguiçosa em `avancarSala(sala, agora)`, chamado a cada leitura/polling e antes de aceitar resposta. Processo único (adapter-node); reiniciar o servidor apaga as salas, o que é aceito de propósito. Salas sem movimento por 6h somem na próxima criação
  - **Fases**: `lobby` → `pergunta` → `revelacao` → (`pergunta` …) → `fim`. Pergunta vira revelação quando o tempo acaba **ou** todos responderam; a revelação espera `ESPERA_REVELACAO_MS = 4000` e avança sozinha. O professor também controla na mão (`iniciar` no lobby, `proxima` na pergunta/revelação) e tem duas saídas: **`encerrar`** ("Encerrar o quiz" — marca `sala.encerrada`: fecha novas entradas e a partida segue normal para quem já está, até o ranking) e **`sair`** ("Sair e remover todos", com `confirm()` — apaga a sala da memória na hora e todo aluno cai em "Sala não encontrada"). `entrarSala` recusa sala `encerrada`/`fim` ("já foi encerrado") além da já começada; `iniciar` continua permitido com a sala encerrada (os que estão no lobby ainda jogam). Código de 6 caracteres sem O/0/I/1 (`ALFABETO_CODIGO`), lido em voz alta
  - **O gabarito não sai do servidor durante a pergunta**: `perguntaEmJogo()` devolve `correta: null` até a revelação (`status === 'revelacao' || 'fim'`), valendo para host e aluno
  - **Pontuação Kahoot**: `pontosDaResposta()` dá de 500 a `PONTOS_BASE = 1000` conforme o tempo que sobrou; erro/omissão é zero. `calcularRanking()` ordena por pontuação (nome como desempate) e quem empata **divide a posição** (1, 1, 3)
  - **API** (`src/routes/api/quiz/sala/[codigo]/+server.ts`): o `GET` é o polling (host se `locals.session`, aluno se `?j=<id>`; `cache-control: no-store`) e o `POST` recebe JSON `{ acao: 'iniciar' | 'proxima' | 'responder', jogadorId?, indice? }`. O **aluno responde por `fetch` POST**, não por form action: uma action `?/x` substituiria a query e perderia o `?j=` que identifica o jogador. O cliente usa `$lib/quiz-cliente.ts` (`buscarEstado`/`enviarAcao`)
  - **Contador no cliente por diferença**: o servidor manda `tempoRestanteMs` no momento da resposta e o cliente recomputa com o próprio relógio (guarda `recebidoEm`), sem depender de os relógios baterem
  - **Editor** (`$lib/components/EditorQuiz.svelte`): título/descrição, cartões de pergunta (2–4 alternativas com rádio da correta, tempo 5–120s), e um `<details>` para **colar um JSON pronto** (`interpretarQuizImportado` aceita `{ titulo?, descricao?, perguntas }` ou array direto, com apelidos de campo e alternativa como string ou `{ texto, correta }`). O rádio da alternativa usa `name` por pergunta. Ao lado de "Importar perguntas" há **"Exportar perguntas"**, que joga o quiz atual (título, descrição e perguntas, **sem `id`** — o parser gera ids novos) no mesmo textarea, então dá para copiar/guardar/reimportar
  - `$lib/quiz.ts` é client-safe (tipos, constantes, normalização `normalizarPergunta(s)`, validação `validarPerguntas`, pontuação, ranking, parser de importação e path helpers `caminhoEditarQuiz`/`caminhoHost`/`caminhoJogar`); `$lib/server/quiz.ts` é o CRUD. Rotas: lista `/quiz`, edição `/quiz/[quizId]/editar`, host `/quiz/host/[codigo]` (exige sessão), aluno em `/quiz/jogar` (código + nome, público) e `/quiz/jogar/[codigo]?j=<id>`
  - **Navbar**: sem sessão (visão do aluno) o menu mostra "Entrar no quiz" → `/quiz/jogar`, para não precisar digitar a URL; com sessão seguem os links de gestão (Apostilas/Anexos/Atividades/Quiz). O `Navbar` decide por `data.user` do `+layout.server.ts`
- Referência de anexo não é posse: `/anexos` lista em quais aulas ele é usado (único por aula) e a action devolve 409 ao excluir anexo em uso, pedindo para remover os links
- **Seções** são catálogo normalizado: tabela `secoes` (`id`, `apostilaId`, `nome`, `ordem`) e `aulas.secaoId` nullable; CRUD no painel da apostila, select no editor, agrupamento na listagem. Nome único por apostila (comparação sem acento/caixa, máx. 120 = `LIMITE_NOME_SECAO`, com `maxlength` nos três inputs de seção — painel de criar/renomear e o criar do editor) e ordenado por `ordem`, com grupo "sem seção" no fim. O SQL do painel (carregar aulas/seções, CRUD de seção e reordenação) fica em `src/lib/server/apostila.ts` — a rota só lê o FormData e traduz o `FalhaPainel`
- SQLite não liga `PRAGMA foreign_keys`: ações que apagam seção/apostila/nullam `aulas.secaoId` por conta própria
- Blocos de conteúdo (JSON em coluna, não tabela filha): texto/cabeçalhos, código, mermaid, imagem, tabela, fórmulas, links, exercício, dissertativa, simulação e html — todos disponíveis como opção, adicionando conforme necessário. `Exercicio.svelte`, `Dissertativa.svelte`, `Simulacao.svelte` e `Html.svelte` editam dentro do próprio card (`EM_CARTAO` no `EditorCanvas`), sem camada de configuração
- **O bloco `titulo` vai de H1 a H6 e o nível é escolhido por botões, não por `select`**: `NIVEIS_TITULO` em `blocks.ts` é a lista valida (o tipo `NivelTitulo` vem dela e `ehNivelTitulo` valida o que vem do POST; fora da lista o bloco é descartado). Na camada de configuração do `EditorCanvas` são seis `btn btn-xs` num `join` com `role="group"`/`aria-label` "Nível do título" e `aria-pressed` no atual, mesmo padrão do seletor de modo do editor: são 6 valores fixos que cabem na linha, então o `select` só custava dois cliques. Cada botão leva `tooltip tooltip-top` + `data-tip="Título N"` da lib (o texto do `::before` **não** entra no nome acessível, que segue sendo o H visível — é o que mantém `getByRole('button', { name: 'H4' })` nos E2E). **Bloco novo nasce em H1** (`criarBloco`), não em H2. As tags saem por `svelte:element this={\`h${nivel}\`}` nos três lugares (`TextoEditavel`, `BlocoRender`, `Apresentacao`), com a escala por nível em `TITULO_CLASSE`/`TITULO_APRESENTACAO` (leitura e slide) e em `.canvas-titulo-{1..6}` (editor, espelha a escala da leitura para o bloco não pular de tamanho ao sair da edição). O `TextoEditavel` leva `role="heading"` + `aria-level` porque o `svelte:element` não tem tag estática para o lint inferir. O canvas passa `rotulo="Editar título"` no bloco de título (o default é "Texto do bloco", e os E2E `inserir-bloco.spec.ts`/`fluxo.spec.ts` que clicam no título casam por esse rótulo)

## ahmardesign — regras (da doc da lib, não óbvias)

- **A lib é a fonte da verdade da UI**: construir com as classes do `ahmardesign` (`btn`, `card`, `select`, `alert`, `tabs`, utilitários de flex/gap/spacing/radius…). Antes de escrever qualquer estilo, verificar se a lib já não resolve — não recriar componentes nem aparência da lib no app
- **CSS local (`<style>` no Svelte) precisa ser justificado**: só quando a lib não tem o que precisa, e no mínimo possível. Nunca estilizar por convenience/ajuste fino o que a lib já cobre
- **Nunca hardcodar o que o tema muda** (raio, cor, espaçamento): usar os tokens/classes do tema, senão o layout quebra em temas quadrados como `brutalist` (`--rounded-box: 0px`). Ex.: raio → classes `.rounded-box`/`.rounded-btn`/`.rounded-badge` ou `var(--rounded-box)`/`.rounded-btn`; no CSS local, preferir a classe da lib
- **A lib vem do registry** (`^1.2.0` no package.json) para o deploy funcionar em qualquer host. Mudança na lib local só entra no app depois de `npm publish` + `pnpm install`; para developar contra o fonte, dá pra apontar temporariamente para `link:../ahmardesign` (symlink/junction) e voltar para `^x.y.z` antes de publicar (ou usar `workspace:` se virar workspace)
- CSS importa no servidor normalmente: `@ahmartecnologias/ahmardesign/ahmardesign.css` via subcaminho do package `exports`
- **O helper JS (`.../ahmardesign.js`) SÓ no cliente** — executa `AHMAR.init()` na carga e acessa `document.body`/`localStorage`: usar import dinâmico em `onMount`, nunca no SSR
- Tema via `data-theme` no `<body>`; `AHMAR.setTheme()`; evento `ahmar-theme-change` no `window` para sincronizar store Svelte
- **Tema sem flash (FOUC)**: o SSR sempre emite `data-theme="brutalist"`, então o `app.html` tem um `<script>` síncrono no início do `<body>` que aplica a chave `ahmar-theme` do localStorage antes de `%sveltekit.body%`. Consequências: a chave é a da lib (`ahmar-theme`, não uma própria) e a lista de temas válidos é duplicada no script — `src/lib/theme.test.ts` falha se as duas divergirem. - `AHMAR.init()` é idempotente — chamar no mount cobre elementos renderizados depois (`{#if}`, blocos dinâmicos)

Três decisões que não refazer: (1) cartão **sem ações** é `<a>` (o cartão inteiro é o link, como na home) e **com ações** é `<li>`, porque botão dentro de link é HTML inválido — daí o container ser `div` na home e `ul` nos painéis, e o `li` do painel solto ser contrato de E2E; (2) a classe do container vem de `classeLista()` em `src/lib/visao.svelte.ts` (`space-y-2` → `grid gap-4 sm:grid-cols-2`) e `ul` aceita `display: grid`, então o container não muda entre os modos; (3) a visão é **uma preferência só do navegador** (`mcurso:visao`, lida por `iniciarVisao()` no mount do `+layout.svelte`, sem FOUC e sem script no `app.html`), compartilhada por aluno e professor — a home é pública, então ela não pode depender da sessão
- **Submissão de form é sempre `use:enviando`** (`src/lib/enviando.ts`): toda submissão POST passa por essa action, que embute o `enhance` e, enquanto a action roda, põe `disabled` + `btn loading` (classe da lib) + `aria-busy` em todos os `button[type="submit"]` do form. Os 20 usos cobrem todos os forms POST do app (login, criar apostila, salvar conteúdo/quiz, os 7 do painel da apostila, `PainelSoltos`, quiz, jogar, responder atividade, importar). Opções: `confirmar?: () => boolean`, `sucesso?: (resultado) => void`, `aoResultado?: (ctx) => void`. Quatro decisões travadas: (1) **o `confirm()` de exclusão passa por `confirmar`, nunca por `onsubmit`** — o `handle_submit` do `enhance` sempre chama `event.preventDefault()` e não olha `event.defaultPrevented`, e o listener direto dele roda antes do `onsubmit` delegado do Svelte, então o confirm no `onsubmit` rodaria com o fetch já em voo; `confirmar` devolvendo `false` chama `cancel()` (sem fetch e sem `ligar`); (2) no sucesso chama **`invalidateAll()` antes do `applyAction`** (é o que o `fallback_callback` do `enhance` faz: reseta o form + invalida os loads) — esquecer isso foi o bug que derrubou 8 E2E, porque o POST voltava 200, o botão saía do `loading` e a lista de `data` (anexos, seções, aulas) ficava velha; (3) `aoResultado` trata o resultado **sem `applyAction`** e só existe no exportar do `/importar` (preserva o comportamento antigo de não mexer nos selects); (4) o `enhance` troca o reload síncrono por fetch + navegação client-side, então **E2E que clica "Entrar"/"Criar" e já navega precisa esperar** a navegação assentar — specs que não esperavam caíram no `/login` (sessão não estabelecida) ou leram a URL antiga. Feedback de fetch fora de form (salvar a ordem, host e jogador do quiz) usa estados locais (`salvandoOrdem`, `comandoEmAndamento`, `alternativaEnviada`)

## Integrações com quirks conhecidos

- Better Auth no SvelteKit precisa `basePath: '/api/auth'` na inicialização do `auth.ts`; o `src/hooks.server.ts` resolve a sessão **antes** de cada request e põe em `event.locals`, e o `svelteKitHandler` ainda atende `/api/auth/*`
- `src/lib/server/auth-cli.ts` é config mínima do Better Auth usada **só** pelo CLI (`@better-auth/cli`) para gerar o `auth-schema.ts`; não é o auth do runtime
- Mermaid roda em SSR? Não — renderizar no cliente (blocos mermaid são típicos candidatos a componente `{#if}`/lazy no SvelteKit)
- Tema do Mermaid é **por bloco** (`tema` em `BlocoMermaid`, default `neutral`, lista em `TEMAS_MERMAID`): muda só `mermaid.initialize({ theme })` e o `$effect` do `Mermaid.svelte` re-renderiza. Valor vindo do POST é saneado em `normalizarCamposBloco` — bloco antigo sem o campo ou com tema fora da lista cai no default, nunca é descartado (o bloco inteiro tem mais valor que o cosmético)
- adapter-node: dependência em `dependencies` fica **externa** no build (resolvida de `node_modules` em runtime); em `devDependencies` é **bundlada**. Por isso o SO do runtime só enxerga `dependencies`. **O app não tem nenhuma dependência nativa**: o SQLite vem do próprio Node (`node:sqlite`, embutido) e o MySQL usa o `mysql2` (JavaScript puro). `ssr.external`/`rollupOptions.external` no vite não funcionam para forçar externalização (rolldown ignora); a regra é o package.json
- **Sem better-sqlite3 (decisão de 12/10/2026)**: nenhum binário nativo do pacote carrega na Hostinger — 13.x traz prebuild no tarball com `linux-x64.node` exigindo **GLIBC_2.29** (`ERR_DLOPEN_FAILED` em `/lib64/libm.so.6`), e o prebuild da 12.x que o `prebuild-install` baixa **também** exige o mesmo símbolo; o fallback de compilação morre no **Python 3.6.8** do host (o gyp moderno do node-gyp precisa de 3.8+ por causa do operador walrus). O host é um container antigo (glibc < 2.29). Por isso o SQLite agora é o **`node:sqlite`** (`DatabaseSync`), embutido no Node ≥ 22.13 (sem flag desde 22.13.0; `engines.node` no package.json). O drizzle estável (0.45.x) não tem driver node:sqlite (só na linha `@rc`/1.0-beta), então o app passa o `DatabaseSync` **direto no driver `better-sqlite3`** do drizzle com shims em `src/lib/server/db/node-sqlite.ts`: a session do driver só usa `prepare().all/get/run`, `prepare().raw().all/get` (modo cru, devolve arrays — embrulhado) e `transaction(fn)` (BEGIN/COMMIT/ROLLBACK — embrulhado, `.deferred/.immediate/.exclusive`). O `DatabaseSync` liga FK por padrão (o better-sqlite3 deixava desligado), então abrimos com `enableForeignKeyConstraints: false`. O `import Client from 'better-sqlite3'` do driver é satisfeito por um **stub `file:`** em `vendor/better-sqlite3-stub` (versão 7.99.0 para satisfazer o peer `>=7` do drizzle; nunca é instanciado porque o app sempre passa a instância). `@types/better-sqlite3` fica em devDependencies só pelas tipagens do driver e do shim. Efeitos: `pnpm db:migrate` manual (drizzle-kit) pode não funcionar sem o pacote real — o app migra no boot, então não faz falta; `pnpm db:generate` segue ok (não conecta no banco)
- **pnpm 11+ mudou a configuração de build e o lugar das settings** (custo de um deploy quebrado na Hostinger): `onlyBuiltDependencies`/`ignoredBuiltDependencies` **saíram** e viraram o mapa **`allowBuilds`** (`pacote: true|false`), e o `strictDepBuilds` passou a **`true` por default** — build não revisado não é mais aviso, é erro (`ERR_PNPM_IGNORED_BUILDS`, "Error: Failed to install dependencies"). Além disso a pnpm 11+ **não lê mais o campo `pnpm` do package.json** (só avisa e ignora), então `overrides` também vive em `pnpm-workspace.yaml`. Por isso o arquivo tem as duas grafias: `allowBuilds` para pnpm ≥10.26/v11+ (o deploy) e `onlyBuiltDependencies`/`ignoredBuiltDependencies` para a local (10.12.4, que ainda não conhece `allowBuilds`) — as chaves antigas podem sair quando a pnpm local for ≥10.26. Hoje a lista tem **só `esbuild`** (o better-sqlite3 saiu do projeto, ver bullet acima)
- **`overrides` do `cookie` REMOVIDO em 12/10/2026 por decisão** (pedido de simplificação; não tinha relação com o erro de deploy — cookie é JS puro): o `@sveltejs/kit` 2.x segue declarando `cookie: ^0.6.0`, então o advisory GHSA-pxg6-pf52-xh8x (nome/path/domain de cookie com caractere fora de faixa) **voltou** ao `pnpm audit`. Risco baixo num app single-user; se um dia quiser zerar o audit, restaurar `overrides: { cookie: ^0.7.2 }` no `pnpm-workspace.yaml`
- **Transação: um corpo só, `async`, nos dois dialetos** (`transacao()` em `src/lib/server/db/transacao.ts`) — é o ponto único que o dialeto troca. No SQLite o shim de `node-sqlite.ts` deixou de recusar callback `async`: ele **fecha a transação quando o promise assenta** (COMMIT no resolve, ROLLBACK no reject; um `desfazer` tolera o rollback já feito). Consequência que não pode ser esquecida: **o corpo de uma transação não pode fazer I/O de verdade** — só consultas ao `db` e código puro, porque cada `await` resolve em microtask e a transação nunca devolve o controle ao event loop (se devolvesse, outra request entraria na mesma transação). O drizzle com o `node:sqlite` continua síncrono por baixo (a session só usa `prepare().all/get/run` e o `raw()`); os corpos ficam nos serviços de `lib/server` (`apostila.ts`, `importar.ts`), nunca nas rotas
- **MySQL/MariaDB (Passo 4)**: três coisas que só aparecem rodando de verdade — (1) **a tabela carrega o mapa de valores** (ver "Modelo de dados"), então `db/tabelas.ts` tem que ser a fonte das consultas; (2) **insert no MySQL não tem `.returning()`** (o drizzle só expõe `$returningId()`, que lê a PK do `insertId` do driver — e devolve vazio se a coluna não for PK autoincremento), então todo insert passa por `inserirId` em `db/inserir.ts`; o `RETURNING` de `update`/`delete` **não** foi mexido (o dialeto MySQL do drizzle monta, e o MariaDB suporta). (3) `datetime`/`timestamp` do drizzle fazem round-trip em UTC (`toISOString` na escrita, `+0000`/`Z` na leitura), o que casa com o `mode: 'timestamp'` (epoch) do SQLite — a única diferença é que `auth-schema.mysql.ts` usa `timestamp(3)` porque é o que o CLI do Better Auth gera; o CLI é a fonte da verdade daquele arquivo e o app nunca compara data em SQL, então fica como está. O `json()` devolve objeto/array pelo próprio `mysql2` (o app já consome com cast) e a conexão é um **pool** (ver o bullet do `wait_timeout`)
- **Migration no boot, não no deploy**: `aplicarMigrations(db, dialeto)` roda dentro de `db/index.ts`, que é importado por `auth.ts` → `hooks.server.ts` no boot, antes de qualquer consulta. Não usar `drizzle-kit migrate` no servidor (é devDependency e a Hostinger pode instalar só `dependencies`); `pnpm db:migrate` continua valendo para a mão. A pasta é **por dialeto** (`PASTAS` em `migrar.ts`: `drizzle`/`drizzle-mysql`, a cópia em `build/`, a original do checkout em `../`, e `MIGRATIONS_DIR` na frente de tudo) e o `pnpm build` copia as duas para dentro de `build/`, então só a pasta de build precisa estar no ar
- `DB_PATH`/`UPLOADS_DIR` em produção precisam estar **fora da pasta de build**: host com build versionado (Hostinger) apaga a pasta a cada deploy, e o banco e os uploads somem junto. No MySQL o que precisa sobreviver é o **banco em si** (`DB_URL`) — não há arquivo no deploy. **O `UPLOADS_DIR` continua sendo arquivo mesmo no MySQL**: o backup gerenciado do banco **não** cobre os uploads, que precisam do backup próprio. Na Hostinger a área é `hbuilds/versions/<build-id>/` (com `current` simbólico e só as **2 últimas** versões guardadas) e a doc é explícita: `hbuilds/` e `public_html` são **sobrescritos a cada deploy** e edição manual por File Manager/FTP/SSH **não persiste** — ou seja, **trocar o deploy para manual não salva um caminho relativo**: o que salva é o caminho absoluto fora dessa área (ex.: `/home/uXXXXXXXX/mcurso/uploads`), com backup próprio. O boot loga o caminho resolvido e avisa quando ele é relativo fora do dev
- **Trocar um deploy para MySQL é só ambiente, nunca código** (o `.env` é **gitignored** — `.env`/`.env.*`, com `!.env.example` —, então o push não leva variável nenhuma e o `.env` de produção segue como estava; o que está versionado é só o modelo). O dialeto é lido de `DB_DIALECT` no `db/index.ts` e o app não muda em lugar nenhum. Armadilhas que já apareceram: a comparação é **exata** (`mysql` minúsculo; `MySQL` cai em SQLite **em silêncio**), sem `DB_URL` o boot **falha de propósito** (mensagem clara) em vez de cair no SQLite, o usuário do banco precisa de **DDL** (o app cria as tabelas no boot) e o banco deve nascer **`utf8mb4`/`utf8mb4_unicode_ci`** (Hostinger confirmada em 18/10/2026: MariaDB 11.8 + essa collation; o app **não tem `LIKE` em SQL** — a busca por título é filtro de tela —, então a collation afeta ordenação, não busca). A variável importa **no build e na subida**: o `vite build` também abre a conexão e aplica a migração (ver quirks), então o banco precisa **existir** antes do build. `DB_PATH` pode ficar no `.env` (ignorado no modo mysql): o **rollback é uma linha** — apagar/comentar o `DB_DIALECT` volta para o SQLite velho, intacto
- **A conexão MySQL é um pool, nunca `createConnection`** (o deploy de 18/10/2026 subiu e ficou em 500 em tudo por causa disso): em hospedagem compartilhada o servidor derruba a conexão parada no `wait_timeout` e, numa conexão única, ela **nunca** volta — a partir daí toda consulta falha com `Failed query: ...` e o app só se recupera reiniciando o processo. O pool (`mysql.createPool({ uri, connectionLimit: 10, maxIdle: 2, idleTimeout: 60_000, enableKeepAlive: true, ... })`) descarta a conexão morta assim que o socket fecha (o `PoolConnection` sai do pool no `end`/`error`) e abre outra na consulta seguinte. Reproduzido local com `kill <id>` no servidor: com `createConnection` o app dá 500 **para sempre**; com o pool a requisição seguinte já responde 200. As transações seguem numa conexão só — o `db.transaction` do drizzle pega uma conexão dedicada do pool e devolve no fim (`transacao.ts` não mudou), e o `maxIdle`/`idleTimeout` são o que faz o cliente fechar a conexão ociosa antes do servidor
- **O 500 do servidor loga a causa** (`handleError` em `hooks.server.ts`): o log padrão do SvelteKit mostra só o erro de fora, e o do drizzle sai como `Failed query: ...`, escondendo o código do MySQL (`PROTOCOL_CONNECTION_LOST`, `ER_NO_SUCH_TABLE`, `ER_ACCESS_DENIED`...) que é o que diz o que aconteceu. Por isso o `handleError` (que substitui o log padrão) loga o erro **e** `error.cause` — sem isso, o deploy de 18/10/2026 ficou sem diagnóstico possível
- **O boot confere que a migração criou tabelas** (`contarTabelas`/`conferirTabelas` em `db/index.ts`, `contarTabelas` em `migrar.ts`): `__drizzle_migrations` pode registrar tudo como migrado num banco **sem tabela nenhuma** (basta o controle ter sobrado de um banco recriado) — o drizzle então pula tudo em silêncio, o log mente "banco em dia" e toda consulta falha com `ER_NO_SUCH_TABLE`. Agora o log traz a contagem (`— 11 tabela(s)`) e, se o banco só tem o controle de migração, o boot **falha com a instrução** (apagar `__drizzle_migrations` e subir de novo) em vez de servir 500
- **O build fala com o banco** (descoberto em 18/10/2026, ao subir o banco local na 11.8.9): o `analyse` do pós-build do SvelteKit **importa o módulo do servidor**, então o `vite build` abre a conexão e roda as migrations — um banco MySQL vazio virou **11 tabelas só com o `pnpm build`**, sem `node build`. Três consequências: (1) com `DB_DIALECT=mysql` o banco precisa **existir antes do build** (senão `ER_BAD_DB_ERROR` e o build morre — foi exatamente o que quebrou a primeira rodada do E2E no MariaDB 11.8.9 novo) e o usuário precisa de **DDL** no build e no boot; (2) por isso o `webServer` do E2E faz o reset **antes** do build (é quem cria o banco); (3) no deploy, criar o banco no painel **antes** de subir o código. Não "consertar" tornando o `db/index.ts` preguiçoso: todas as consultas importam `db`/`tabelas` no topo, o custo não compensa
- Arrasto de listas é genérico em `src/lib/arrastar.ts`: o item usa `{@attach arrastar(opcoes)}` e o container `data-arrasto-lista={grupo}`; `data-arrasto-item` marca cada item e `data-arrasto-alca` a alça (o arrasto só começa nela, para não sequestrar seleção/caret do `TextoEditavel`). `moverItem` faz o splice local e as classes `.arrastando`/`.arrasto-alvo(-fim)` vivem no `app.css` (a lib não tem estilo de arrasto)
- Sobram **3 advisories** no `pnpm audit` (1 moderado + 2 low) e todos são **aceitos de propósito**: o moderado é `esbuild <=0.24.2` via `drizzle-kit > @esbuild-kit/esm-loader` (devDependency, não vai pro bundle; advisory é do `esbuild --serve`, nunca rodamos; forçar 0.25 no loader pinado em 0.24 arrisca quebrar `db:generate` — reavaliar quando o drizzle-kit trocar o loader); os 2 low são **`cookie`** (voltou com a remoção do override — ver bullet acima) e **`katex`** via `mermaid` (pré-existente)
